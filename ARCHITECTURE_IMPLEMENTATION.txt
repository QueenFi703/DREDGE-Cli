🔧 CORE COMPONENTS
═══════════════════

1. DAG EXECUTION ENGINE (dredge_run_pipeline)
   ═════════════════════════════════════════════

   Entry Point: dredge_run_pipeline(input_data, pipeline_type="standard")

   Features:
   - Async/await execution throughout
   - Automatic topological sorting for dependencies
   - Parallel-ready architecture
   - Cache layer integration
   - Telemetry tracking

   Execution Flow:
   1. Create pipeline (standard or ios_swift)
   2. Build DAG with nodes
   3. Topologically sort by dependencies
   4. Execute nodes in order
   5. Cache results
   6. Track telemetry
   7. Return results + telemetry


2. NODE SYSTEM (6 specialized nodes)
   ═════════════════════════════════

   a) IngestNode
      - Ingests raw input data
      - Normalizes input format
      - Default entry point

   b) TranslateNode
      - Format translation (e.g., text → embeddings)
      - Provider integration
      - Fallback support

   c) NormalizeNode
      - Data validation
      - Applies fallback providers
      - Ensures data quality

   d) ExecuteNode
      - Actual computation
      - Model inference
      - Result generation

   e) CacheNode
      - Redis-backed persistence
      - Local fallback cache
      - Memoization

   f) TelemetryNode
      - Event logging
      - Metrics collection
      - Observation


3. PROVIDER SYSTEM (Multi-provider failover)
   ════════════════════════════════════════

   a) DeepProvider
      - Semantic analysis
      - Intent detection
      - Entity extraction
      - Sentiment analysis

   b) GoogleProvider
      - Translation (multi-language)
      - NLP capabilities
      - Vision support

   c) ProviderChain
      - Primary provider with fallbacks
      - Automatic failover
      - Circuit breaker pattern
      - Success rate tracking

   d) ProviderRegistry
      - Central provider management
      - Chain orchestration
      - Health monitoring


4. CACHE LAYER (Dual-tier caching)
   ═════════════════════════════════

   Tier 1: Redis
   - Distributed caching
   - Persistence across restarts
   - TTL support (default 3600s)

   Tier 2: Local
   - In-memory fallback
   - Fast access
   - Process-specific

   Cache Key Generation:
   - Deterministic (MD5 of input)
   - Node-aware
   - Pipeline-scoped


5. TELEMETRY SYSTEM (Comprehensive observability)
   ═══════════════════════════════════════════════

   Metrics Tracked:
   - Event count
   - Success rate (per provider)
   - Average latency
   - Cache hit rate
   - Consecutive failures
   - Execution duration

   Events Logged:
   - pipeline_start
   - node_executed
   - cache_hit / cache_miss
   - provider_failure
   - pipeline_complete

⚡ PROVIDER FAILOVER EXAMPLE
════════════════════════════

Scenario: Translation request arrives

1. Try Primary: GoogleProvider
   - Call /translate API
   - Record latency: 150ms
   - Cache result

2. If GoogleProvider fails:
   - Increment failure counter
   - Try Fallback: DeepProvider
   - Record failure event
   - Record alternative latency: 200ms

3. If DeepProvider also fails:
   - All providers exhausted
   - Raise exception
   - Log failure telemetry
   - Return error to client

4. Circuit Breaker:
   - After 5 consecutive failures → UNHEALTHY
   - Mark provider unavailable
   - Skip in future attempts
   - Automatic recovery possible


🔒 CACHING STRATEGY
═════════════════════

Cache Key Format:
  dredge:cache:{MD5(node_id + input_data)}

Example:
  dredge:cache:abc123def456...

Cache Flow:

1. Check Redis:
   - If hit → return cached result, mark CACHED
   - If miss → continue

2. Execute node:
   - Call provider
   - Measure latency
   - Get result

3. Store in cache:
   - Set in Redis (with TTL)
   - Set in local cache
   - Mark cache_key in metadata

4. Next identical request:
   - Cache hit immediately
   - No provider call needed
   - Return in <1ms
